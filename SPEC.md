# AI Study Planner — Functional Specification

Status: initial MVP requirements. This is intended behavior, not an inventory of implemented features. Product scope is defined in [PROJECT.md](PROJECT.md); presentation is defined in [DESIGN.md](DESIGN.md).

## 1. Core domain entities

### Common conventions

- IDs are opaque, stable identifiers generated by the backend. The exact representation is an implementation choice.
- Creation and update timestamps are server-managed UTC instants. Deadlines represent timezone-aware instants, displayed in the student's profile timezone.
- Availability and session dates and times are local to that profile timezone. Backend conversion must handle daylight-saving boundaries explicitly and reject ambiguous or nonexistent local times unless resolved by the user.
- The MVP uses dated availability, a Monday-to-Sunday displayed week, and one personal workspace per authenticated student. Changing timezone must preserve existing scheduled instants and be handled as a validated planning change.
- Work is entered in hours but normalized to whole minutes for allocation and accounting, using one documented conversion rule across services. Unrepresentable precision must be rejected or normalized visibly.

### User

Supabase Auth provides identity; the application profile stores display name, avatar path and the fixed Europe/Budapest timezone. Email/password are not duplicated in PostgreSQL application tables.

| Field | Meaning |
| --- | --- |
| id | Stable student identifier. |
| display_name | Name shown in the interface. |
| timezone | IANA timezone used for local dates, deadlines, and weekly reporting. |
| created_at, updated_at | Profile lifecycle timestamps. |

All core records have a server-derived user_id. Authenticated SQLAlchemy sessions, PostgreSQL RLS and same-owner parent foreign keys enforce isolation. Legacy NULL-owner rows are quarantined until an explicit administrator claim; new users start empty. Shared workspaces remain out of scope. See docs/authentication.md for the complete implemented contract.

### Subject

| Field | Meaning and constraints |
| --- | --- |
| id | Stable identifier. |
| name | Required, nonblank subject name. |
| description | Optional text. |
| color | Validated accessible subject color token or hex color. |
| created_at | Creation timestamp. |
| updated_at | Last modification timestamp. |

A subject has zero or more tasks. Color is a display aid, never the only identifier.

### Task

| Field | Meaning and constraints |
| --- | --- |
| id | Stable identifier. |
| title | Required, nonblank task title. |
| description | Optional assignment details. |
| subject_id | Required reference to an existing subject. |
| deadline | Required timezone-aware due instant. Date-only input resolves to the end of that date in the profile timezone and is shown explicitly. |
| estimated_hours | Positive estimate of total work at the current estimate revision. |
| remaining_hours | Nonnegative work still required; cannot exceed estimated_hours. |
| priority | LOW, MEDIUM, or HIGH. Default: MEDIUM. |
| difficulty | EASY, MEDIUM, or HARD. Default: MEDIUM. |
| progress | Percentage from 0 to 100, consistent with the effort rules below. |
| status | TODO, IN_PROGRESS, COMPLETED, or CANCELLED. Default: TODO. |
| created_at, updated_at | Lifecycle timestamps. |

Progress and remaining hours must not be independent competing sources of truth. Working MVP rule: estimated and remaining effort are canonical; progress is derived as `100 × (estimated_hours - remaining_hours) / estimated_hours`, rounded for display. Entering progress in a form updates remaining effort through a backend service using the same normalization rules. Reject contradictory values sent together.

New tasks normally start with remaining_hours equal to estimated_hours and progress zero; existing work can be entered at creation. Increasing an estimate retains remaining effort unless a revised value is provided, subject to consistency validation. The UI should allow adjusting both so previously completed work can be represented accurately. When remaining work exceeds the old total estimate, the student must revise the total as well.

COMPLETED implies remaining_hours zero and progress 100. Zero remaining effort transitions to COMPLETED. Nonzero progress normally implies IN_PROGRESS, but IN_PROGRESS with zero progress is allowed when work has started without measurable completion. CANCELLED preserves effort values but excludes the task from scheduling and active risk. Reopening a completed or cancelled task is an explicit update with consistent remaining work and status.

### Availability

| Field | Meaning and constraints |
| --- | --- |
| id | Stable identifier. |
| date | Local study date. |
| start_time | Local start time. |
| end_time | Local end time, strictly after start_time on the same date. |

Availability describes capacity, not a reservation or completed study time. A date may contain several non-overlapping windows. Overnight availability is entered as separate windows on consecutive dates. Recurring availability rules are deferred; the MVP accepts explicit dated windows.

### StudySession

| Field | Meaning and constraints |
| --- | --- |
| id | Stable identifier. |
| task_id | Required reference to a task; the subject is obtained through that task. |
| date | Local session date. |
| start_time, end_time | Local interval on the same date. |
| planned_minutes | Positive duration, equal to the elapsed duration of the scheduled interval. |
| completed_minutes | Reported actual study time, initially zero. |
| status | PLANNED, COMPLETED, MISSED, or PARTIALLY_COMPLETED. |
| origin | MANUAL or SCHEDULER. Legacy rows are MANUAL; explicit user placement is protected. |

PLANNED is a future or ongoing reservation. COMPLETED means the planned session was finished; MISSED has zero completed minutes; PARTIALLY_COMPLETED has more than zero but less than planned_minutes. The initial MVP records completed_minutes between zero and planned_minutes; extra work is recorded separately through a task progress update, without inventing extra historical sessions.

Actual study time and task effort progress are distinct: time spent does not prove equal work completed. Recording a session outcome therefore also accepts updated remaining effort or explicit confirmation that no progress was made. The backend updates task progress and session outcome atomically. Merely generating, moving, or missing a session does not reduce remaining work. A completed session need not complete its task.

Session outcomes must be recorded once per revision: retries cannot deduct effort twice. Edits to historical outcomes require a consistent correction to task effort rather than replaying a deduction blindly.

### Derived planning and risk results

Planning responses contain the planning interval, evaluation time, resulting sessions, unallocated minutes per task, and reasons for constraints or conflicts. Replanning also reports created, changed, removed, and preserved future sessions.

Risk responses contain task_id, level, remaining minutes, usable capacity before the deadline, allocated minutes before the deadline, shortfall where applicable, evaluation time, and machine-readable reasons with display explanations. These are backend-derived results; persistent caching is optional and must never serve a known stale assessment as current.

## 2. Subject management

- Create, list, inspect, and edit subjects, including name, description, and color.
- Show related tasks and their backend-provided progress summary.
- Allow deletion of a subject only when it has no tasks. Otherwise explain that tasks must first be reassigned or deleted; do not cascade silently.
- Preserve task and session relationships when changing subject metadata. Refresh affected labels and colors.

Acceptance: editing a subject name changes its display across tasks and the calendar without moving sessions; deleting a subject with tasks returns an actionable validation error.

## 3. Task management

- Create, list, inspect, update, and delete tasks with the fields and enums above.
- Filter by subject, status, priority, deadline range, and current risk; support useful deadline and priority sorting.
- Record progress through backend effort rules, with consistent status updates.
- Changes to deadline, effort, priority, difficulty, or active status trigger affected planning and risk recalculation when a plan exists. Descriptive edits alone do not move sessions.
- Completing or cancelling a task removes its future PLANNED sessions, frees capacity, and preserves recorded outcomes.
- Explicit task deletion requires a UI confirmation explaining that its linked sessions and recorded history will also be deleted. Perform deletion atomically and refresh summaries and the affected plan. Prefer cancellation when history should be retained.
- Permit overdue tasks to be entered or edited. Show overdue status and risk; never fabricate a feasible schedule before an elapsed deadline.

Acceptance: a completed task never receives automatic allocations; changing its title cannot change another task's schedule.

## 4. Availability management

Students add, view, edit, and remove dated windows in their local timezone. Multiple windows per day are allowed; overlapping windows are rejected with a clear explanation so capacity cannot be counted twice. Adjacent windows are valid and may be treated as contiguous by the planner.

Show free capacity after existing reservations. Reducing or deleting availability triggers replanning for affected future sessions and any competing work that must move. Completed and partial historical outcomes remain intact even when historical availability changes. Reject edits that would invalidate an ongoing session unless the student first records or resolves its outcome.

Acceptance: removing a future two-hour window either moves its work into valid remaining capacity or exposes unallocated work and refreshed risk.

## 5. Planning engine

### Inputs

- Active TODO and IN_PROGRESS tasks with deadline, priority, difficulty, and remaining effort.
- Dated availability intersecting the requested planning interval.
- Existing sessions, their statuses, actual outcomes, and any explicit placement constraints from a manual or assistant request.
- Profile timezone, an explicit evaluation instant, and versioned planning configuration.

The primary UI displays a week. Generation accepts an explicit interval; risk analysis must still inspect relevant capacity through each task's deadline, including dates outside the displayed week. Work outside the requested generation interval is not silently scheduled.

### Required behavior

1. Validate and normalize the snapshot before allocation.
2. Consider deadline urgency, priority, remaining work, difficulty, availability, and existing sessions when ordering and allocating tasks.
3. Favor urgent work and distribute work within actual free capacity. Difficulty influences ordering or block suitability, not an unexplained increase in required hours.
4. Split large tasks across multiple sessions when necessary, using configurable duration limits whose defaults will be documented before engine implementation.
5. Create no overlapping sessions and no allocations outside availability, before the evaluation time, or after a deadline. A session may end exactly at the deadline.
6. Do not allocate more future minutes to a task than its remaining effort. Existing valid allocations must count toward that amount and against shared capacity.
7. Preserve historical outcomes and ongoing sessions. Reuse valid future sessions when possible rather than replacing them on every invocation.
8. Return unallocated work and clear reasons if the constraints cannot be satisfied. Never overbook to conceal an infeasible request.
9. Use stable tie-breaking for equivalent tasks. The same snapshot, configuration, interval, and evaluation time must produce equivalent allocations without duplicates on repeat requests.

The first implemented scheduling policy is greedy-v1, specified in [docs/scheduler.md](docs/scheduler.md): local due-date urgency, explicit priority, exact deadline, unreserved effort, difficulty, and task ID establish a stable ordering. It adds 60-minute target blocks to safe available time while preserving every existing session. Future policy refinements require a documented version and must preserve these invariants; the risk engine remains read-only and separate from future replanning.

### Outputs and acceptance

Return sessions and a per-task allocation summary with allocated and unallocated minutes. Business services validate and persist the result atomically, checking that the input state has not changed while planning. A conflict must trigger a fresh calculation or a clear retry response, never a stale overwrite.

Acceptance scenarios include two competing deadlines, equal-ranked tasks, no availability, work exceeding capacity, a task smaller than the preferred block size, adjacent windows, and an already overdue task. Feasible work is allocated without overlap; infeasible work remains visible. A request to plan an overdue task needs a revised deadline or an explicit user-selected recovery block with an overdue warning.

## 6. Deadline risk engine

The backend assigns LOW, MEDIUM, or HIGH risk to active tasks. Risk is a deterministic assessment, not a probability or LLM opinion.

| Level | Intended meaning |
| --- | --- |
| LOW | Sufficient feasible capacity with comfortable slack under the configured policy. |
| MEDIUM | Feasible work with limited slack or growing time pressure. |
| HIGH | Serious capacity pressure or likely shortfall requiring attention. |

Inputs include remaining hours, usable hours before deadline, progress, deadline proximity, priority, existing reservations, and competing active tasks. Progress must be interpreted consistently with remaining effort rather than counted as a separate deduction.

Capacity must not be promised independently in full to every task. Evaluate competing demand with the planning engine's consistent allocation model. Explain whether reported capacity is free time or time already allocated to that task; unrelated reservations cannot be counted as free time. Evaluate risk through the deadline, not only through the visible week.

For example, a report due in three days with eight hours remaining and only three usable hours has a five-hour shortfall and warrants HIGH risk. The implemented capacity-v1 thresholds and accounting rules are specified in [docs/risk-engine.md](docs/risk-engine.md).

Completed and cancelled tasks have no active risk. Overdue active tasks are HIGH. Missing availability is treated as zero entered capacity and explained; missing or invalid inputs produce a validation issue rather than a fabricated LOW result.

Recalculate risk after relevant task, availability, or session changes and when time advances enough to change the assessment. Store or return the evaluation time so stale data can be identified. Acceptance includes competing tasks, zero capacity, deadline boundaries, progress updates, overdue work, and reproducible results for identical inputs.

## 7. Automatic replanning

The first implementation is explicit preview/apply (`affected-v1`), documented in [docs/replanning.md](docs/replanning.md). No CRUD edit automatically runs the replanner. Future generated reservations may await approved repair after constraints change; manual/ongoing guard rules remain enforced. Preview is read-only, Apply revalidates a snapshot/diff fingerprint, and only affected future planner-managed sessions inside the requested horizon may change. Fully automatic reconciliation below remains a later extension.

Replanning coordinates the existing planning and risk engines. It must preserve history, count only remaining work, and limit changes to affected future allocations and dependent conflicts.

| Trigger | Required response |
| --- | --- |
| Missed session | Record MISSED with zero study time; keep remaining work unchanged; allocate that outstanding work into remaining valid capacity. |
| Partially completed session | Record actual study minutes and revised remaining effort; allocate only outstanding task effort. |
| Task estimate or remaining effort changes | Reconcile allocated minutes with revised remaining work, then adjust affected sessions and risk. |
| Deadline changes | Reconsider allocations against the new deadline, moving invalid blocks and reporting shortfalls. |
| Availability changes | Move or split invalid future blocks and recalculate competition for the remaining windows. |
| Priority, difficulty, completion, or cancellation changes | Reassess affected ordering, release unneeded reservations, and refresh risk. |

An elapsed PLANNED session with no reported outcome is treated as MISSED when backend reconciliation next runs. Reconcile on plan/dashboard reads and relevant mutations; an always-running job is not required for the MVP. This is a conservative assumption of zero reported study time, clearly shown with an option to correct it. The system cannot observe whether the student actually studied.

For each trigger: reconcile outcomes, identify affected tasks and windows, preserve unaffected valid sessions, recalculate affected allocations, validate constraints, persist changes together, and return a change summary plus refreshed risks. Newly displaced work can expand the affected set; a whole-week rebuild is unnecessary unless the constraints actually require it.

Completed, missed, and partially completed records are history. Remaining work is placed in new future sessions rather than moving a historical record. Ongoing sessions remain reserved until resolved. Repeated reconciliation or action retries must not create duplicate sessions or repeat effort updates.

Acceptance: after a missed Tuesday two-hour block, outstanding work is moved or split into free time before the deadline, other feasible unrelated sessions retain their IDs and times, and any shortfall is visible. If no replacement time exists, return the updated risk and unallocated work without claiming success.

## 8. Dashboard requirements

Dashboard metrics are calculated by backend services using a common profile timezone and explicit reporting period. The frontend formats and renders the values.

| Display | MVP definition |
| --- | --- |
| Tasks completed | Count of currently COMPLETED tasks; label as a total, not completions this week unless completion timestamps are added. |
| Study time this week | Sum of reported completed_minutes on sessions in the current local Monday-to-Sunday week; planned time is shown separately. |
| Upcoming deadlines | Active task deadlines in the next seven days, with overdue work shown separately. |
| Overall progress | Effort-weighted completion across non-cancelled tasks: completed estimated effort divided by total estimated effort. Empty denominator displays “No tasks.” |
| Today's priorities | Backend-ranked active tasks and today's sessions, with deadline/risk reasons. |
| Weekly study plan | Sessions for the selected week and their outcomes. |
| Study workload | Planned minutes versus available minutes per day, plus unallocated work. |
| Subject progress | Same effort-weighted progress grouped by subject, excluding cancelled tasks. |
| Deadline risks | Active tasks with risk badges, reasons, remaining work, capacity, and relevant actions. |

Provide loading, empty, error, and infeasible-plan states. Zero reported time must not appear as a loading placeholder. Completed totals describe current task status, not an immutable historical completion count. Changing estimates can change progress percentages; the UI should explain this where the estimate is edited.

Acceptance: calendar, dashboard, deadlines, and assistant show consistent figures for the same backend snapshot and reporting interval.

## 9. AI assistant requirements

The assistant supports requests such as “What should I focus on today?”, “What is my most risky deadline?”, “Create a plan for this week”, “I did not finish this task”, “Move this task to Friday”, and “Add a focus block tomorrow.”

The backend supplies current tasks, sessions, availability, priorities, risk results, evaluation time, and profile timezone as needed. The LLM interprets intent, chooses allowed actions, and explains their confirmed results. It cannot calculate authoritative allocations or treat generated text as saved state.

| Action | Responsibility |
| --- | --- |
| create_task | Validate required task data and create a real task. |
| update_task | Apply validated field, progress, or session-outcome changes through business services. |
| get_today_plan | Return today's persisted sessions and backend-ranked priorities. |
| generate_schedule | Invoke deterministic planning for an explicit interval. |
| reschedule_task | Request a valid alternative allocation for a task within user constraints. |
| get_deadline_risks | Return backend-calculated risk levels and reasons. |
| create_focus_block | Reserve a task-linked study session using the same availability, deadline, overlap, and remaining-effort rules. |

The final transport schemas remain open. These actions describe service capabilities, not permission for arbitrary database operations. Session outcome changes made through update_task must use the same atomic outcome service as the regular session UI.

- Resolve relative dates against the profile timezone and show the resolved date in the result.
- Ask for a task or time clarification when a reference is ambiguous or required data is absent.
- For “I did not finish”, obtain actual study time and remaining effort; do not assume zero progress or mark a task completed.
- For “Move to Friday”, pass a placement constraint to the backend. Explain conflicts or alternatives if Friday cannot accommodate the work.
- For a focus block, obtain the task and duration or use clearly documented backend defaults. A generic block without a task is outside this initial domain model.
- Report success only after the service confirms persistence. Distinguish proposed actions from completed actions, and refresh displayed state afterward.
- Validate action names, parameters, record ownership, and identifiers server-side. Treat task descriptions and chat text as data, not authority to bypass these controls.
- Keep provider credentials in the backend. Handle timeouts, unavailable providers, and invalid tool arguments without corrupting state or inventing a successful result.

Acceptance: responses about priorities and risk agree with backend data; ambiguous moves prompt clarification; rejected actions leave valid state intact. Assistant failure does not disable normal application screens. A mock assistant in the UI phase must be visibly identified as a demo.

## 10. API expectations

The application exposes REST resources and command-style planning operations. Exact paths beyond these groups, request/response schemas, pagination, and status-code details are to be finalized during backend design.

| Group | Responsibilities |
| --- | --- |
| /subjects | Subject CRUD and subject-level summaries. |
| /tasks | Task CRUD, filters, lifecycle, and effort/progress updates. |
| /availability | Dated study windows and validation of capacity changes. |
| /study-sessions | Read calendar sessions, record/correct outcomes, and request validated manual adjustments. |
| /planner | Generate a plan, retrieve planning summaries, and coordinate affected replanning. |
| /risks | Return current task-level assessments and risk summaries with evaluation time. |
| /assistant | Accept messages, supply backend context, dispatch allowed actions, and return explanations and action results. |

Dashboard and progress aggregates can be served by a small read service; their final endpoint placement is open. An AI action and its equivalent REST operation must call the same business service. Responses must distinguish validation failures, missing resources, concurrency conflicts, provider failures, and valid but infeasible plans. Infeasibility is a domain result with shortfall data, not an unexplained server error.

Mutation responses must supply refreshed data or identify what to refresh. Use consistent timestamp and enum representations, structured field errors, and retry-safe planning/outcome commands. Do not expose AI credentials or provider-specific objects as application contracts.

## 11. Validation rules and verification

- Reject invalid or nonexistent dates, malformed timestamps, blank required names, unknown enum values, and invalid references.
- Accept valid past deadlines for overdue work; overdue is a domain condition, not an invalid date.
- Require positive estimated hours, nonnegative remaining hours no greater than the estimate, and progress between 0 and 100 consistent with effort.
- Require end_time after start_time and reject invalid local-time conversions. Use half-open intervals: one session ending at 19:00 can be followed by another starting at 19:00.
- Reject overlapping availability and overlapping scheduled/reserved study sessions for the student. Validate historical actual-time corrections for consistency as well.
- Require future reservations to fit availability and task remaining effort. Automatic scheduling must respect the task deadline; an explicit overdue recovery block must be labeled as such.
- Exclude COMPLETED and CANCELLED tasks from automatic scheduling and active deadline risk.
- Enforce session duration and outcome invariants and prevent double counting of study time or effort on retries.
- Preserve history during replanning; destructive task deletion is a separate explicit operation.
- Recalculate affected risk and summaries after mutations; never leave a known invalid future plan presented as valid.

Backend tests must cover effort/status consistency, capacity accounting, planner determinism, deadline boundaries, risk determinism, competing tasks, partial/missed outcomes, minimal replanning, retries, and timezone boundaries. Integration checks should exercise persistence and API validation; final workflow checks should cover mock-to-real UI integration and assistant action results. Exact formulas and thresholds require tests when selected.

## Working assumptions and decisions to refine

Initial assumptions: one student profile; IANA timezone; Monday-start weeks; dated availability without recurrence; task-linked focus blocks; effort-derived progress; explicit reported time separate from effort; conservative missed-session reconciliation on access; subject deletion guarded by references; task deletion removes its related history after an explicit warning.

Open before relevant implementation: scheduling weights and tie-break details, preferred/minimum/maximum block duration, normalization precision, risk thresholds, database representation, exact API contracts, and assistant provider. Refine these in this document before introducing behavior dependent on them. These decisions must stay within the documented MVP unless scope is explicitly changed.


## Authentication and account layer

Supabase Auth provides confirmed email/password sign-up/sign-in, persistent sessions, recovery/password reset, sign-out and optional configured Google OAuth. Protected routes do not load planner state before identity resolution. Sign-out/account switch disposes old entities, risks, previews and dialogs, ignores late responses and loads a fresh owner-scoped workspace. API 401 returns to sign-in without automatic retry loops.

Profiles support display name, private avatar, Auth-sourced email display and fixed Europe/Budapest timezone. Account deletion requires typed DELETE confirmation and a server-side admin action targeting only the verified principal, with Storage cleanup and Auth/profile/core cascades. No service-role credential is exposed to React. Auth URL/keys, confirmation/redirect/Google configuration, private Storage policies, migration/legacy handling and live acceptance steps are specified in [docs/authentication.md](docs/authentication.md). Planning effort, priority, DST, risk and replan policies are unchanged.
